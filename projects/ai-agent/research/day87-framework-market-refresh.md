# Day87 Framework and Job-Market Refresh

## Decision boundary

Day87 refreshes evidence; it does not choose or install a framework. The fixed
repository baseline is `bd58209db97e8cbb5901ec81577237143e59b1ba`. All records
were collected into an isolated classroom copy. No formal repository, Provider,
Tool, database, broker, permission service or production runtime was changed.

The comparison is bounded to LangGraph, OpenAI Agents SDK and PydanticAI. A
candidate name discovered in a job posting does not automatically enter the
candidate set. Candidate frequency is a market signal, never architecture
authority.

## Evidence rule

Every claim keeps its supported scope, freshness, conflicting evidence,
confidence, publisher/source type, observed version, published/updated date and
retrieval time. Checked-source silence becomes `UNKNOWN` or
`NOT_FOUND_IN_CHECKED_SOURCES`; it never becomes `UNSUPPORTED`.

Current official documentation, repositories, releases, registries, official
ATS pages and company career pages are primary evidence. Search summaries and
aggregators can discover a source but cannot prove an active job or a framework
contract. Invalid or replaced snapshots remain in history as
`INVALID`/`SUPERSEDED` and are excluded from current scoring.

## Application-owned hard constraints

The framework must remain behind a replaceable application Adapter. Generated
Tool candidates cannot authorize or dispatch themselves. Immediately before an
effect, the application must recheck current tenant, grant, approval, operation
identity, policy and fence facts. Persistent framework memory cannot replace
authoritative database facts. A built-in handoff cannot replace the Day85
delegated-grant, claim/lease/fence, result-verification and fan-in contracts.

Official feature documentation can establish a narrow native feature claim. It
cannot prove the complete Day79-Day86 composition. An application-boundary hard
constraint requires an executed discriminating spike for the observed version.

## Candidate evidence snapshot

- LangGraph has the strongest checked documentation for persistence,
  checkpointing and interrupt/resume behavior. Its documented node restart
  semantics make idempotency important. Exact Day82-Day86 contract fit remains
  `UNKNOWN` or `ADAPTER_REQUIRED`, not assumed native.
- OpenAI Agents SDK identity and current release metadata were established.
  High-level Agent, Tool, handoff and tracing capabilities were observed, but
  checked sources did not establish the exact durable-job, approval-binding and
  application-owned security contracts. Those cells remain `UNKNOWN`.
- PydanticAI exposes typed Agent/Tool concepts and advertises durable-execution
  integrations. The checked graph API is beta. GitHub and the visible PyPI
  snapshot disagreed on the observed version, so current package identity is
  `UNKNOWN_PENDING_REFRESH` until reconciled.

No framework is selected on Day87.

## Job sample boundary

The classroom sample contains 12 deduplicated, active, primary-source postings
from 9 companies. It spans the US, Israel, India, Latin America, Singapore,
Europe and remote wording, but it is still senior-heavy, regionally uneven and
concentrated by company: Fluid AI contributes three distinct roles and Klaio
two. Distinct roles count separately; mirrors of the same canonical posting do
not.

The sample supports only a dated, bounded observation that Python, backend
engineering, cloud/container operations, evaluation, observability and security
are recurring transferable signals. `X or equivalent` is a general competency
plus a named example. It is not proof that X is universally required.

The sample cannot establish global market share, global geographic demand,
future trends, employment probability, a hiring guarantee, or the correct
application architecture.

## Day88 handoff

Readiness is `MORE_EVIDENCE_NEEDED`. Candidate B remains a provisional label,
not a winner. Day88 should run one discriminating spike:

> Route every candidate-framework Tool call through the application Adapter,
> recheck current authorization immediately before dispatch, and prove that
> direct framework dispatch, stale approval, revoked grant and stale fence paths
> all fail closed.

The spike must record the exact candidate package/version, configuration,
runtime, fake/real boundaries, commands, results and retrieval/execution time.
Passing this spike proves only that scoped version/configuration boundary. It
does not settle other hard constraints or production readiness.
