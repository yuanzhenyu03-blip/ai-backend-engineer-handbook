## Teaching outcome so far

The learner can distinguish framework features, application-contract fit and
production evidence. The learner consistently rejected claims that persistence,
HITL, memory, multi-Agent orchestration, popularity or freshness alone satisfy
the existing application contracts.

The learner identified the principal hard constraint: all Tool calls must remain
after the application Adapter and current authorization check. Learning ease was
correctly classified as a weighted preference. The learner selected candidate B
only as a provisional comparison candidate, not as a final framework choice.

## Learner reasoning demonstrated

The learner concluded that:

- a framework cannot dispatch Tools before coordinated boundary validation;
- current permissions must be bound and rechecked;
- framework memory is not authoritative durable business truth;
- a built-in handoff is incomplete without the application coordination contract;
- official evidence should take priority;
- evidence needs scope, freshness, conflicts, confidence, publisher/source type,
  observed version, published/updated date and retrieval time;
- framework familiarity does not define the candidate set;
- repeated framework mentions cannot override hard constraints;
- official ATS pages should be retained over mirrors;
- job evidence must distinguish required, preferred and incidental signals;
- closed and unknown postings do not count as active;
- role-first Agent-framework job queries reduce LangGraph sampling bias;
- US-heavy evidence cannot support global claims;
- newest evidence is not automatically the most stable evidence;
- outcome-unknown dispatch preserves the original operation ID for reconciliation;
- invalid snapshots and their downstream conclusions must be preserved but marked
  `INVALID`/`SUPERSEDED`;
- a sensitivity flip requires a Day88 discriminating spike;
- a decision-critical unknown yields `MORE_EVIDENCE_NEEDED`.

## Misconceptions and incomplete answers corrected

1. **Distinct roles at one company** — three Fluid AI roles may count separately
   because their titles, responsibilities and canonical URLs differ. Company
   concentration must still be disclosed.
2. **Validator identity** — the learner initially called the Day87 validator
   candidate-framework production integration code. It is offline research and
   decision-protection code; `22/22 PASS` proves only those deterministic rules.
3. **Sample inference** — when the learner did not know the boundary, the sample
   was limited to dated observations and explicitly excluded global trends,
   hiring probability and architecture authority.
4. **Spike meaning** — a passing boundary spike proves one version/configuration
   and one scoped hard constraint, not every contract or production readiness.

## Instructor-authored final synthesis

This synthesis was produced by the instructor at the learner's request.

Day87 is a research and decision-safety checkpoint, not a framework-selection
or application-integration day. It compares LangGraph, OpenAI Agents SDK and
PydanticAI against the application-owned Day79-Day86 contracts. Framework
documentation establishes only narrow feature claims; it does not automatically
prove durable Job/Attempt identity, exact human-approval binding, authoritative
business-state persistence, delegated handoff/fan-in semantics or security
admission.

The non-negotiable boundary is that every framework-generated Tool call remains
behind the application Adapter. Current authorization, tenant, approval, grant,
operation identity, policy and fence facts are rechecked immediately before the
controlled dispatcher performs an effect. Popularity, learning ease and job
mentions are weighted preferences and cannot compensate for an unproved hard
constraint.

The 12 active postings from 9 companies show only a dated, bounded sample of
transferable skill signals. Required, preferred and incidental mentions remain
separate; `X or equivalent` does not become an X-specific mandate. Geographic,
seniority and company-concentration biases prevent global-market, future-demand
or hiring-probability claims.

Candidate B cannot be selected today because its central authorization boundary
is still `UNKNOWN`, and the illustrative ranking changes under small weighting
changes. The honest handoff is `MORE_EVIDENCE_NEEDED`. Day88 should run a
version-pinned, replaceable-adapter spike proving that direct dispatch, revoked
grant, stale approval and stale fence paths fail closed. Even a PASS would prove
only that scoped version/configuration and not production readiness.

The Day87 Python is offline evidence-validation code in an isolated classroom
copy. It does not import a candidate framework or alter the application runtime.
